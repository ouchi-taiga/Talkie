## 1. アーキテクチャ

### 1.1 全体構成

```text
ブラウザ (Svelte 5 + Tailwind + shadcn-svelte)
    ↓ HTTP
Vercel (SvelteKit サーバーサイド = バックエンド)
    ↓ Drizzle ORM (postgres.js)
Supabase (PostgreSQL + Storage)
```

SvelteKit をフルスタックで使う。別のバックエンドサーバーは立てない。
`+page.server.ts` / `+server.ts` / `$lib/server/**` のコードはサーバーでのみ実行され、
ブラウザには送信されない。DB 接続情報をここで扱ってよい根拠がこれ。

### 1.2 技術選定

| 領域           | 採用                                | 選定理由                                                                                            |
| -------------- | ----------------------------------- | --------------------------------------------------------------------------------------------------- |
| フレームワーク | **SvelteKit** (fullstack)           | フロントとバックを1プロジェクトで完結                                                               |
| UI             | **Svelte 5 (Runes)**                | `vite.config.ts` で `runes: true` を強制済み                                                        |
| CSS            | **Tailwind CSS v4 + shadcn-svelte** | shadcn-svelte で初期化済み (`style: vega`, `baseColor: neutral`, icons: lucide)。DaisyUI は使わない |
| DB             | **Supabase (PostgreSQL)**           | 画像ストレージと DB を1サービスで賄える。PostgreSQL は経験あり                                      |
| ORM            | **Drizzle** (安定版 0.45.x)         | `sv add drizzle` で公式アドオンがある。SQL に近く発行クエリが読めるため学習に向く                   |
| 認証           | **Better Auth**                     | `sv add better-auth` で公式アドオンがある。認証テーブルが自分の DB に入り Drizzle で管理できる      |
| 画像保存       | **Supabase Storage**                | DB には URL のみ持つ。無料枠 1GB                                                                    |
| 多言語         | **Paraglide JS** (inlang)           | `sv add paraglide` で公式アドオンがある。コンパイル時に関数化され tree-shake される。§6.8           |
| 並べ替え       | **svelte-dnd-action**               | **タッチとマウスの両対応**。runes と衝突するレガシー API を使っていない。§6.3                       |
| デプロイ       | **Vercel**                          | `sveltekit-adapter=vercel`                                                                          |
| 画像書き出し   | `html-to-image` 等                  | 実装時に選定                                                                                        |

### 1.3 選定の経緯 (再検討時の判断材料)

- **ORM: Drizzle vs Prisma** — Prisma は経験があり、v7 で Rust エンジンが廃止されて
  サーバーレスの弱点も解消済み。それでも Drizzle を選んだのは「新しいものを使ってみたい」
  という学習目的と、SvelteKit 公式アドオンの存在から。
  **ただし Drizzle は 2026-08 時点で pre-1.0** (安定版 0.45.2、v1.0.0-beta が 18ヶ月継続、
  安定版は 2026-03 以降更新停止)。リスク緩和は §5.2 に記載。
- **認証: Better Auth vs Supabase Auth** — Supabase Auth の方が実装量は少ないが、
  認証データが Supabase 側に閉じるため DB 移行時に歪な構成になる。Better Auth は
  認証テーブルを自分の DB に持つため、認証・認可の学習にもなり移植性も高い。
- **DB: Supabase vs Neon** — Neon の Object Storage は beta かつ単一リージョン。
  画像保存が要件にあるため Supabase を採用。
  Supabase は **7日間非アクティブでプロジェクトが一時停止**する点に注意 (再開は可能)。

### 1.4 バージョン方針

- **Node.js: >= 24** (`package.json` の `engines` に明記)
- **TypeScript: 6 系で開始し、7 系への更新を見据える** (§5.3)
- **Drizzle: 安定版 (0.45.x) を使う。** v1.0.0-beta は本番投入しない

## 2. ディレクトリ構成とレイヤー分離

### 2.1 レイヤー

```text
src/routes/**/+page.svelte        画面 (UI のみ)
src/routes/**/+page.server.ts     入出力の変換・認証チェック
src/lib/server/services/          ビジネスロジック       ← ここに集約
src/lib/server/db/                DB アクセス (Drizzle)  ← 差し替え可能に保つ
```

**守るべきルール2つ:**

- **DB アクセスは `$lib/server/db/` に閉じる。** ORM 固有のコードを他の場所に書かない。
  Drizzle が pre-1.0 であることのリスク緩和と、将来の ORM 変更に備える
- **ビジネスロジックを `+page.server.ts` に書かない。** 将来バックエンドを別言語
  (Rust 等) に移す場合、ロジックが SvelteKit のファイル規約に埋まっていると移植できない

### 2.2 想定するファイル配置

```text
messages/                    翻訳ファイル (ja.json / en.json)  ← Paraglide

src/

    components/
      ui/                    shadcn-svelte のコンポーネント (自動生成)
      chat/                  チャットプレビュー (§3.5)
        ChatScreen.svelte    layoutId からコンポーネントを引く
        layouts/             レイアウトごとの実装
          messenger/

      editor/                エディタ関連
    themes/                  見た目の定義 (§3.5)
      types.ts               Layout / Skin の型

      skins.ts               Skin の一覧 (色の値)
```

## 3. データモデル

### 3.1 ER 図

```text
user (Better Auth が管理)
 ├─< session      (Better Auth)
 ├─< account      (Better Auth)
 └─< project                       作品
       ├─< character               登場人物
       └─< message                 発言
             └── characterId ──> character
```

### 3.2 テーブル定義 (MVP)

Better Auth が生成するテーブル (`user` / `session` / `account` / `verification`) は
ライブラリの定義に従うため、ここではアプリ固有のテーブルのみ記載する。

#### project — 作品

| 列          | 型          | 制約                   | 備考                                             |
| ----------- | ----------- | ---------------------- | ------------------------------------------------ |
| id          | uuid        | PK                     |                                                  |
| userId      | text        | FK → user.id, NOT NULL | 所有者                                           |
| title       | text        | NOT NULL               | 作品の管理名。一覧に出る。チャット画面には出ない |
| chatTitle   | text        | NOT NULL               | チャット画面のヘッダーに出す名前                 |
| memberCount | integer     | NULL 可                | ヘッダーに出す人数。NULL なら1対1。§3.5 参照     |
| layoutId    | text        | NOT NULL               | 画面レイアウト。§3.5 参照                        |
| skinId      | text        | NOT NULL               | 配色・着せ替え。§3.5 参照                        |
| createdAt   | timestamptz | NOT NULL               |                                                  |
| updatedAt   | timestamptz | NOT NULL               |                                                  |

- index: `(userId, updatedAt desc)` — 一覧を更新日時順で引くため
- `layoutId` / `skinId` を project に持たせることで、**後から見た目を変更できる**
  (要件 §3.5)。発言データは見た目に依存させない
- **`memberCount` がグループかどうかの判定を兼ねる。** NULL なら1対1とみなし、
  ヘッダーの人数と、相手の名前 (吹き出しの上) を出さない。
  実際のチャットアプリも1対1では相手の名前を出さないため、フラグを別に持たない

#### character — 登場人物

| 列          | 型                   | 制約                                         | 備考                                |
| ----------- | -------------------- | -------------------------------------------- | ----------------------------------- |
| id          | uuid                 | PK                                           |                                     |
| projectId   | uuid                 | FK → project.id, ON DELETE CASCADE, NOT NULL |                                     |
| name        | text                 | NOT NULL                                     | 表示名                              |
| side        | enum('self','other') | NOT NULL                                     | 自分 / 相手。吹き出しの左右を決める |
| bubbleColor | text                 | NOT NULL                                     | 吹き出し色                          |
| avatarUrl   | text                 | NULL 可                                      | Supabase Storage の URL             |
| sortOrder   | integer              | NOT NULL                                     | 一覧の並び順                        |

#### message — 発言

| 列          | 型                                   | 制約                                         | 備考                                     |
| ----------- | ------------------------------------ | -------------------------------------------- | ---------------------------------------- |
| id          | uuid                                 | PK                                           |                                          |
| projectId   | uuid                                 | FK → project.id, ON DELETE CASCADE, NOT NULL |                                          |
| characterId | uuid                                 | FK → character.id, NULL 可                   | system / date では NULL                  |
| type        | enum('text','image','system','date') | NOT NULL                                     | 発言タイプ                               |
| body        | text                                 | NULL 可                                      | text / system / date の本文              |
| imageUrl    | text                                 | NULL 可                                      | type=image のときの画像 URL              |
| time        | text                                 | NULL 可                                      | 吹き出しの脇に出す時刻。"12:34" の文字列 |
| isRead      | boolean                              | NOT NULL default false                       | 既読表示                                 |
| sortOrder   | integer                              | NOT NULL                                     | 表示順。§3.3 参照                        |
| createdAt   | timestamptz                          | NOT NULL                                     |                                          |

- index: `(projectId, sortOrder)` — 表示順で引くため
- **`type='date'` は会話の区切りに出す日付ラベル** (「今日」「1月1日(月)」)。
  日付計算はせず `body` に文字列をそのまま入れる。創作物なので実在の日付である
  必要がなく、ユーザーが自由に書けた方がよい
- **`time` は日時型で持たない。** 実際の送信時刻ではなく表示上の演出なので、
  文字列で持つ。「25:99」のような架空の時刻も書ける

### 3.3 並べ替えの順序管理

**`sortOrder` は integer の連番 (0 始まり)。並べ替えたら全件振り直す。**

D&D ライブラリは並べ替え後の配列を返すので、その添字をそのまま入れる。

```ts
items.map((item, i) => ({ ...item, sortOrder: i }));
```

更新は1回のクエリでまとめて行う。この規模なら全件更新でも問題にならない。

### 3.4 画像の扱い

- 画像本体は **Supabase Storage** に置き、DB には URL のみ保存する
- DB に Base64 で直接持つ方式は採らない (データ量が 1.33 倍に膨らみ、無料枠 500MB を
  すぐ使い切る)
- パス構成は実装時に決める。ユーザー単位で分離し、他人の画像を参照できない構成にする
- **お試しモード (未ログイン) では Storage を使わない。** 画像は Blob URL または
  Base64 でブラウザ内に置くだけにする (サーバーへ送らない)

### 3.5 見た目の設計 (Layout × Skin の2軸)

チャット画面の見た目を**2つの独立した軸**で持つ。

| 軸         | 内容                                                 | 例                        |
| ---------- | ---------------------------------------------------- | ------------------------- |
| **Layout** | 画面の構造。ヘッダー・入力欄のアイコン、吹き出しの形 | `messenger` / `social`    |
| **Skin**   | 配色。将来は壁紙やフォントも入る (着せ替え)          | `green` / `blue` / `dark` |

2軸なので**掛け算で増える**。レイアウトを1つ足せば全スキンで使え、スキンを1つ
足せば全レイアウトで使える。`project` は `layoutId` と `skinId` の両方を持つ。

**どちらも DB のレコードではなくコード内の定義として持つ。** 開発側が用意する
もので、ユーザーが作るものではない。DB に置くとデザイン調整のたびに
マイグレーションが必要になる。

#### 持ち方が軸によって違う

| 軸         | 持ち方                    | 理由                               |
| ---------- | ------------------------- | ---------------------------------- |
| **Layout** | **Svelte コンポーネント** | 構造は値で表現しきれない (後述)    |
| **Skin**   | **値** (色の集合)         | 色はレイアウトをまたいで使い回せる |

**Layout を値で持たない理由:** ヘッダーに並ぶアイコンの種類・順序・間隔や、
入力欄の作りはレイアウトごとに違う。`headerIcons: string[]` のような形で
抽象化しても、アイコンが増えるたびに型を書き換えることになり、配置の違いも
表現できない。**レイアウトごとにコンポーネントを用意し、アイコンは直接書く。**

```text
src/lib/themes/
  types.ts          Layout / Skin の型
  layouts.ts        Layout の一覧 (id と表示名のみ)
  skins.ts          Skin の一覧 (色の値)

src/lib/components/chat/
  ChatScreen.svelte      layoutId からコンポーネントを引く
  layouts/
    messenger/
      Screen.svelte      組み立て。連続発言の判定もここ
      Header.svelte      検索・電話・カレンダー・メニュー
      Footer.svelte      プラス・カメラ・写真・マイク (飾り。入力はできない)
      Bubble.svelte      吹き出し。時刻・既読・アイコン
      SystemLine.svelte  システムメッセージと日付ラベル
    social/
      ...
```

- **Skin はコンポーネントが props で受け取る。** スキンを増やしても
  コンポーネントは変更しない
- **`if (layoutId === 'messenger')` のような分岐を書かない。** 分岐を書くと
  追加のたびに全コンポーネントを触ることになる
- **ID は削除・改名しない。** 既存の作品が参照しているため。
  廃止する場合は一覧から隠すだけにする

#### 表示のきまり

- **相手の名前は、グループのときだけ吹き出しの上に出す** (`memberCount` で判定)
- **連続した発言ではアイコンと名前を省く。** アイコンの場所は空けて位置を揃える
- ヘッダーと入力欄は**書き出し時に含めるかを選べる**ようにする (§6.4)。
  プレビューには常に出す

**実在サービスのロゴ・名称を含めない** (要件 §3.5)。§7 も参照。

### 3.6 お試しモード (未ログイン) のデータ保持

未ログイン時は DB を使わず、**ブラウザ内 (localStorage) だけにデータを置く**。

- DB と同じ型を使い、保存先だけを差し替える構成にする
  (`$lib/storage/` に「DB 版」と「localStorage 版」を用意し、同じインターフェースで扱う)
- **引き継ぎ処理は作らない** (要件のスコープ外)
- **iOS では数週間の未使用で localStorage が消去されることがある。**
  さらに script-writable storage には 7日の上限がある。
  → 「保存されません」の明示と、書き出しを促す導線が必須 (要件 §3.2)

## 4. 認証・認可

### 4.1 認証

**Better Auth** を使う。認証テーブルは自分の DB (Supabase PostgreSQL) に置き、
Drizzle でスキーマを管理する。

- MVP はメール + パスワード認証で開始する
- セッションは Cookie で保持する

### 4.2 認可の方針

**RLS (Row Level Security) は使わず、アプリケーション層で認可する。**

#### 理由

- Drizzle が接続文字列のロールで接続すると **RLS はバイパスされる**。
  ポリシーを書いても効かないという事故が起きやすい
- 認可ロジックが DB ポリシーではなくアプリ層にある方が、将来バックエンドを
  差し替える際に移植しやすい (§2.1)
- 「認可をアプリ層で実装する」経験自体が学習目的に含まれる

#### 実装ルール

- **すべてのクエリで所有者を検証する。** 作品・キャラクター・発言の取得・更新・削除では
  必ず `userId` による絞り込みを行う
- 検証は `$lib/server/` 配下に閉じ、`+page.server.ts` / `+server.ts` から呼ぶ
- **子テーブル (character / message) への操作も、親 project の所有者を検証する**

### 4.3 DB 接続方式

Vercel のサーバーレス関数は起動・終了を繰り返すため、接続数が枯渇しないよう
**Supabase の接続プーラー (Supavisor) を経由する**。

| 用途                           | 接続先                           |
| ------------------------------ | -------------------------------- |
| アプリからの通常接続           | transaction mode / **port 6543** |
| マイグレーション (drizzle-kit) | session mode / **port 5432**     |

- transaction mode は prepared statements が使えないため、接続時のオプション指定が必要
- 環境変数は `DATABASE_URL` (6543) と `DIRECT_URL` (5432) の2つを持つ

## 5. 拡張性・可用性

「バックエンドを差し替えられる」「技術更新に追従できる」状態を保つ。

### 5.1 レイヤー分離

§2.1 を参照。これが拡張性の中核。

### 5.2 Drizzle が pre-1.0 であることへの対処

- **安定版 (0.45.x) を使う。** beta は使わない
- **`drizzle-kit push` は開発時のみ。** 本番は必ず `generate` → `migrate`。
  `push` は確認なしで列を drop することがある
- マイグレーション SQL はリポジトリにコミットして履歴を残す

### 5.3 TypeScript 7 への更新を見据える

TypeScript 7 は Go による書き直しで型チェックが約10倍高速。**正式リリース済み**
(2026-08 時点で 7.0.2) だが、以下の理由で 6 系で開始する。

- `svelte-check` の TS7 対応状況が未確認
- Drizzle (pre-1.0) と Better Auth の TS7 での検証が薄い可能性がある

**更新に備えてやること:**

- `tsconfig.json` で `strict: true` を維持する
- 型を明示的に書き、暗黙の `any` を残さない
- **MVP 完成後、テストが揃った段階で更新を試す** (壊れたかどうかを機械的に判定できる)

### 5.4 その他の将来検討

| 項目                         | 状況                                                                        |
| ---------------------------- | --------------------------------------------------------------------------- |
| Bun への移行                 | 保留。Vercel の実行時は Node ランタイムのため利益が限定的。MVP 完成後に検討 |
| Capacitor でのアプリ化       | Web 完成後                                                                  |
| バックエンドを Rust 等に分離 | §2.1 の分離を守っていれば可能。現時点では予定なし                           |

## 6. 画面設計

### 6.1 画面一覧

| パス                  | 画面                              | 認証     |
| --------------------- | --------------------------------- | -------- |
| `/`                   | ランディング                      | 不要     |
| `/try`                | お試しエディタ (保存なし)         | **不要** |
| `/login`, `/signup`   | ログイン・サインアップ            | 不要     |
| `/projects`           | 作品一覧                          | 必要     |
| `/projects/new`       | 新規作成 (レイアウト・配色を選ぶ) | 必要     |
| `/projects/[id]`      | エディタ (メイン画面)             | 必要     |
| `/projects/[id]/play` | 再生モード                        | 必要     |
| `/settings`           | 設定                              | 必要     |

`/try` と `/projects/[id]` は**同じエディタコンポーネントを使い、保存先だけを
差し替える** (§3.6)。画面を2つ作らない。

### 6.2 エディタ画面

**トーク画面の上で直接編集する。** 編集用の画面を別に持たない。
見ている画面がそのまま編集対象であり、書き出される絵でもある (要件 §3.6)。

#### 編集モードとプレビューモード

| モード         | 出すもの                                                 |
| -------------- | -------------------------------------------------------- |
| **編集**       | ドラッグ用のつまみ、追加用の点線の吹き出し、選択中の枠線 |
| **プレビュー** | 何も足さない。**書き出される絵と同じ状態**               |

- **書き出しはプレビューの状態で行う。** 編集用の要素が写り込まないようにする
- スマホではオーバーレイの表示/非表示と連動させる (オーバーレイを隠す = プレビュー)
- チャット画面のコンポーネントは `editing` を props で受け取り、

#### 判定は画面幅で行う

| 幅        | 作品設定     |
| --------- | ------------ |
| `lg` 以上 | 左パネル     |
| `lg` 未満 | オーバーレイ |

**タッチデバイスかどうかでは判定しない。**

- サイドパネルを置けるかは**幅の問題**であって、指かマウスかの問題ではない
- タッチ対応ラップトップは `pointer: fine`、マウスを繋いだタブレットは
  `pointer: coarse` を返すなど、入力方法での判定は端末によってずれる
- **SSR と相性が悪い。** サーバーには `window` がないため、JS で判定して分岐すると
  ハイドレーション不一致か、一瞬別のレイアウトが見える現象が起きる。
  CSS のメディアクエリなら SSR の出力に含められるので起きない

`pointer: coarse` の使い道は**操作対象を大きくすることだけ**。小さくするのには使わない。

```css
@media (pointer: coarse) {
	.drag-handle {
		min-height: 44px;
	} /* 指で押しやすく */
}
```

#### 操作の割り当て

| 操作                 | 結果                                      |
| -------------------- | ----------------------------------------- |
| 吹き出しをタップ     | その場で本文を編集 (インライン編集)       |
| 吹き出しを長押し     | 操作メニュー (既読・時刻・削除・話者変更) |
| つまみを縦にドラッグ | 並べ替え                                  |
| つまみを横にドラッグ | 話者の変更 (左 = 相手、右 = 自分)         |
| 末尾の点線をタップ   | 種別を選んで発言を追加                    |

- **タップは編集、長押しはメニュー。** タップにメニューを割り当てると編集できない。
  また、スクロールとの誤操作を避けるため長押しにする
- **点線の吹き出しは末尾に常設する。** 途中への挿入は「追加してから並べ替え」で行う。
  タップすると種別 (テキスト / 画像 / システム / 日付) を選ぶ小さなメニューを出す
- 画像を選んだ場合は `<input type="file" accept="image/*">` を開く。
  お試しモードでは Blob URL のままブラウザ内に置く (§3.4)
- キャラクターの編集は、設定パネルからと**アイコンのタップ**の両方から行えるようにする

#### ドラッグ＆ドロップ (並べ替え)

**採用: `svelte-dnd-action`**

選定理由:

- **タッチとマウスの両対応。** `touchstart` / `touchmove` を mouse と同等に実装しており、
  むしろ**ネイティブ HTML5 DnD を明示的に無効化している** (`ondragstart = () => false`)。
  モバイル用のポリフィルが不要
- **runes と構造的に衝突しない。** `svelte/store` / `createEventDispatcher` / `onMount` /
  `svelte:component` を一切使っていない。イベントは native `CustomEvent`
- キーボード操作とスクリーンリーダー対応が標準搭載。読み上げ文言は
  `setAriaStrings` で日本語化できる

**却下した候補:** `@atlaskit/pragmatic-drag-and-drop` は HTML5 DnD 基盤のため
タッチ端末での不具合報告が多く、該当 Discussion がメンテナ未回答のまま放置されている。
モバイルが主要ターゲットの本件では使えない。ネイティブ HTML5 DnD も同じ理由で不採用。

**実装上の注意 (ハマりどころ):**

```svelte
<script lang="ts">
	import { dndzone, type DndEvent } from 'svelte-dnd-action';
	import { flip } from 'svelte/animate';

	let items = $state<Message[]>([]);
	const flipDurationMs = 200;

	// consider(ドラッグ中) と finalize(確定) の両方で必ず「再代入」する
	function handleConsider(e: CustomEvent<DndEvent<Message>>) {
		items = e.detail.items;
	}
	function handleFinalize(e: CustomEvent<DndEvent<Message>>) {
		items = e.detail.items;
	}
</script>

<section
	use:dndzone={{ items, flipDurationMs, delayTouchStart: true }}
	onconsider={handleConsider}
	onfinalize={handleFinalize}
>
	{#each items as item (item.id)}
		<div animate:flip={{ duration: flipDurationMs }}>...</div>
	{/each}
</section>
```

- **`items = e.detail.items` と再代入する。** ミューテートでは動かない。
  action には `$state` プロキシではなく値のスナップショットしか渡らないため
- **`{#each}` にキー `(item.id)` が必須。** 各 item に一意な `id` が必要
- **`delayTouchStart: true` を必ず付ける** (既定 80ms)。
  スマホでスクロールとドラッグの誤判定を防ぐ。最適値は実機で調整する
- **`svelte:element` でラップしない。** 既知の不具合 (item が不可視になる) がある。
  素の `<div>` で包む
- `onconsider` / `onfinalize` を使う (Svelte 5 形式。`on:` は非推奨)
- 並べ替え確定後、`sortOrder` (§3.3) を計算して保存する

**つまみ (ハンドル) 方式にする。** 吹き出し全体をドラッグ可能にすると、
タップでの編集や画面のスクロールと競合する。つまみだけをドラッグ対象にすれば
構造的に競合しない。つまみは編集モードでのみ出すので、プレビューでは見えない。

#### 横方向のドラッグ (話者の変更) は段階的に進める

`svelte-dnd-action` は**縦の並べ替え用**で、「左に出したら相手、右なら自分」という
判定は標準機能にない。ドロップ位置を見て `side` を書き換える処理を自分で書くことになる。
縦の並べ替えと同時に成立するかは**実際に作らないと分からない** (斜めに動かしたときに
どちらの操作とみなすかが曖昧になる)。

1. まず**縦の並べ替えだけ**を実装して動く状態にする
2. その上で横方向を試す
3. 縦の並べ替えと競合して破綻するなら、**長押しの操作メニューから話者を変更**する
   方式に切り替える

要件 §3.6 では横ドラッグを望ましい形としているが、代替手段も用意しておく。

### 6.4 PNG 書き出しの設計

要件 §3.7 の2形式に対応する。

| 形式           | 実装方針                                                 |
| -------------- | -------------------------------------------------------- |
| 長尺1枚        | プレビュー要素全体を1枚の画像に変換                      |
| 画面サイズ単位 | 一定の高さで区切って複数枚生成。**発言の途中で切らない** |

- 分割時は吹き出しの境界で区切る。ページをまたぐ発言が出ないようにする
- 日本語フォントの埋め込みが必要 (Web フォントを使う場合、画像化前に読み込み完了を待つ)

#### iOS で端末に保存する方法 (重要)

**iOS Safari では「写真に保存」が出ないことがある。** Web Share API で共有シートに
「ファイルに保存」しか出ない事例が報告されている (iOS 16 時点。2026 年現在の状況は
未確認のため **iPhone 実機での検証が必要**)。

書き出しはこのアプリの中核機能なので、**確実な経路を主にする**。

| 優先 | 方法                                                | 保存先         |
| ---- | --------------------------------------------------- | -------------- |
| 1    | **生成画像を `<img>` で表示し、長押しで保存させる** | **写真アプリ** |
| 2    | Web Share API (`navigator.share`) でファイル共有    | 共有シート次第 |
| 3    | `<a download>` でダウンロード                       | ファイルアプリ |

- **1 を主経路にする。** iOS の標準的な画像保存操作なので Web Share API の
  不具合に影響されない。実装も単純
- 2 が使える環境では併用する (`navigator.canShare` で判定)
- PC では 3 が自然なので、環境に応じて出し分ける

**実装の早い段階で iPhone 実機で検証する。** ここが満たせない場合、
Capacitor 化 (Filesystem プラグインでカメラロールへ直接保存) を検討する
唯一の技術的な理由になる。

### 6.6 状態管理とサーバー保存

**編集の即時性を優先する。** 入力のたびにサーバーへ送ると遅延が出るため、
以下の2段構えにする。

1. ローカルの状態 (`$state`) を即座に更新 → 画面に反映
2. サーバー保存はまとめて行う (一定間隔、または操作単位)

保存中の表示や失敗時のリトライをどう扱うかは実装時に決める。
未ログイン時は 2 が localStorage への保存になる (§3.6)。

- 設定は localStorage に保存する (ログイン前でも効くようにする)

### 6.8 多言語対応 (i18n)

**採用: Paraglide JS v2** (`sv add paraglide`)。要件 §3.10 に対応する。

```sh
# ja を baseLocale にするため ja を先頭に置く
npx sv add paraglide="languageTags:ja,en"
```

選定理由:

- **`sv add` の公式アドオンがある。** SSR・cookie・`<html lang>` 属性・型生成という
  間違えやすい部分を用意してくれる
- **コンパイル時に型付き関数へ変換され、未使用の翻訳が tree-shake される**
- **`m.settings_language()` のような関数呼び出しで使う。** ストアではないので
  runes 方針 (`$` 構文を使わない) と整合する

**却下した候補:** `svelte-i18n` はストアベースで `$t('key')` を前提とし、runes 方針に
反する。かつ 2024-10 以降更新なし。`sveltekit-i18n` は 2023 年から放置。

#### 重要な設計判断: URL 方式ではなく cookie 方式にする

```ts
// vite.config.ts の paraglideVitePlugin に指定する
strategy: ['cookie', 'preferredLanguage', 'baseLocale'];
```

- **URL に `/ja/` `/en/` を付けない。** 設定画面のトグルで切り替える要件に合う
- **cookie ならハイドレーション不一致が構造的に起きない。**
  サーバーとクライアントが同じ値を見るため
- **`localStorage` を strategy に入れてはいけない。** 初回リクエストでサーバーから
  見えず、サーバーとクライアントで違う言語になる
- `preferredLanguage` を挟むと初回訪問者をブラウザの言語設定で判定できる
- **未ログインでも効く** (cookie なので DB 不要)。要件 §3.10 を満たす

#### 導入時にやること

`sv add paraglide` は **URL 方式を前提としたファイルを作る**ため、掃除が必要。

- `src/hooks.ts` (`reroute` フック) を削除する
- `src/routes/+layout.svelte` に入る `display: none` のロケールリンク集を削除する
- `vite.config.ts` に上記 `strategy` を追記する
- `src/lib/paraglide/` は生成物。`.gitignore` はアドオンが面倒を見るが、
  **`.prettierignore` と eslint の対象外にする必要がある** (未整形で `npm run lint` が落ちる)

#### 言語切替の実装

**`setLocale()` は既定でフルリロードする。これを変えない。**
`{ reload: false }` というオプションがあるが、公式が「通常の言語切替に使うな」と
警告している。リロードすれば cookie がサーバーに渡り再 SSR されるため、
不整合が起きない。

#### 将来: ユーザーごとに言語を DB 保存する場合

Paraglide v2 の **`custom-*` strategy** で後付けできる。`getLocale` が async なので
Better Auth のセッションから引いて DB を参照できる。

```ts
strategy: ['custom-userPreference', 'cookie', 'preferredLanguage', 'baseLocale'];
```

ただし毎リクエストで DB を叩くことになるため、**まず cookie 単体で始める**。
DB は「別デバイスへの引き継ぎ用」として、`setLocale` 時に両方書く形が軽い。

#### 言語を追加する手順 (要件 §3.10 の「後から追加できる」)

1. `project.inlang/settings.json` の `locales` に追加する
2. `messages/{locale}.json` を作る

UI のコードは変更不要。`locales` は runtime から export されるので、
設定画面の `{#each locales}` がそのまま増える。翻訳漏れは型エラーで分かる。

## 7. 商標・法務上の設計制約

実在のメッセージアプリ風のデザインを扱うため、**設計段階で織り込む必要がある制約**。
無料の個人ツールと、収益を得るツールではリスクの評価が変わるため、
最初から回避する形で作る。

### 7.1 分かっている事実

- LINEヤフーのブランドガイドラインは「**事前承諾なしのブランド資産の使用は禁止**」と
  明記しており、企業ロゴ・サービスロゴ・テキスト表記・ドメイン名が対象
- Apple の審査ガイドライン 5.2 も第三者商標の無許諾使用を禁止している
- 既存の類似アプリは**正確なロゴを使わず、名称も直接使用を避けている**
  (「某SNS風」等の婉曲表現を使い、汎用デザインに寄せている)

### 7.2 設計に落とす制約

| 制約                                   | 実装への影響                                                 |
| -------------------------------------- | ------------------------------------------------------------ |
| **ロゴ・アイコン画像を同梱しない**     | テーマにロゴ画像を含めない。アイコンはユーザーがアップロード |
| **テーマ名に実在サービス名を使わない** | `green` / `blue` / `dark` 等の中立な ID と表示名にする       |
| UI・説明文でも実在サービス名を使わない | 「LINE風」等の文字列をコードにもコピーにも書かない           |
| なりすまし・詐欺目的の利用を禁止する   | 利用規約に明記する。書き出し画像への注記オプションも検討     |

- テーマが再現するのは**配色・吹き出しの形・レイアウトの雰囲気**まで
- 課金を始める前に**知財に詳しい弁護士へ相談する** (要件 §7.3)
